## Context

[`ARCHITECTURE.md`](../ARCHITECTURE.md) described the system in prose only — every structural section
was a stub and the repo had zero diagrams. Hand-drawn pictures rot: nothing checks that they still
match reality, and there is no second reviewer here to notice when they drift. The repo already leans
hard on one discipline — **one definition, many generated views, and CI fails on stale generated
code** (the boundary contract, the config schema). We wanted the architecture layer to inherit that
same discipline: a single checkable model that generates its own diagrams, versioned beside the code.

## Decision

Adopt **LikeC4** as architecture-as-code. The model lives in `.likec4` files under
[`docs/architecture/`](../architecture/README.md) and is the single source of truth for a C4 Context
and Container view. It is:

- **Validated** — `likec4 validate` exits non-zero on an undefined element, an unresolved
  relationship, or an invalid view. This is the property none of the alternatives offered.
- **Rendered browser-free, as an SVG carrying what Mermaid dropped** — `likec4 gen dot` emits DOT
  text: the graph structure *and* every element's description, technology and icon, none of which
  `likec4 codegen mermaid` (this record's original choice, rev 3 and earlier) carries at all. That
  text is rendered to SVG by the system Graphviz `dot` binary CI installs beside the LikeC4 toolchain
  — still no headless browser, the same property the Mermaid path held, just performed by Graphviz
  itself rather than the WASM copy of it LikeC4 bundles for its own internal layout. The rendered
  SVG is embedded in `ARCHITECTURE.md` as a plain image reference, the same marker-spliced mechanism
  the Mermaid fence used. A committed `model.json` snapshot (`likec4 export json`) was tried and
  dropped: it had no consumer, and its internal relation ids are not deterministic across machines,
  so it could never pass the staleness gate — a future consumer regenerates it on demand instead.
- **Staleness-gated** — `just check-arch` (and the `architecture` CI job, byte-identically)
  regenerates every generated output — the artifacts under `docs/architecture/` and the diagram
  spliced into `ARCHITECTURE.md` — and runs `git diff --exit-code` on them, extending the "CI fails
  on stale generated code" rule to the architecture layer. Byte-identity across re-renders is
  confirmed empirically (#115); the one non-deterministic byte Graphviz emits — a
  `<!-- Generated by graphviz version N -->` header comment — is stripped by
  [`scripts/render-arch-svg.py`](../../scripts/render-arch-svg.py) before the artifact is compared or
  committed, so the gate's only variable stays the model.
- **Published a second way, ungated: the full interactive site.** `likec4 build` — the same model,
  read once by the one `arch-export` recipe that also produces the gated diagram — emits a
  standalone web application with the requirements/architecture tag view and the per-element
  relationships a merged edge in any static render loses; neither the DOT/SVG render above nor the
  Mermaid path it replaced carries either. It is published to GitHub Pages, following
  [ADR 0029 rev 1](0029-api-explorer-swagger-ui.md)'s precedent shape for an ungated, interactive
  companion to a gated static artifact, and it is **not** staleness-gated — a browser-shaped
  JavaScript application is exactly what this record's browser-free posture keeps out of a gate, so
  it is produced but never diffed. [§ Consequences](#consequences) states what that leaves unverified.

The model is authored so Component and Code levels — and source `link`s into `backend/`/`frontend/` —
can be **added later without restructuring** (LikeC4 nests elements additively). Neither is built
here: no application code exists, so building them would be an abstraction with a single
implementation and no second consumer ([`CONTRIBUTING.md`](../../CONTRIBUTING.md)'s review checklist,
question 8, *Generality*). That ground holds for the Code level and is answered for the Component
level, which [ADR 0019 rev 8](0019-boundary-at-what-deploys-and-tag-tier.md) builds — superseding this
record in that part alone.

## Alternatives considered

- **D2 / Graphviz DOT** — text-to-diagram, but no *model*: they render whatever you write, including
  references to things that do not exist. No validation of undefined elements or dangling
  relationships, which was the whole point. This is about **hand-authoring** a diagram directly in
  D2 or DOT syntax, bypassing LikeC4's model and its validation entirely — a different question from
  rev 4's `likec4 gen dot`, which is LikeC4's own codegen target, read from the validated model the
  same way `codegen mermaid` was. Rendering that generated DOT text with Graphviz does not reopen
  this rejection: nothing here is hand-authored, and the model is still what is validated.
- **Mermaid by hand** — GitHub renders it natively (zero tooling), but it is a drawing, not a model:
  duplicated node ids, no compiler, nothing to fail CI on drift. We still *use* Mermaid — but as
  LikeC4's generated output, not the source of truth. (Superseded at rev 4: LikeC4's Mermaid codegen
  itself is dropped as the committed target, for the reason below.)
- **Structurizr** — a real C4 model with validation, but the good rendering path is the hosted/cloud
  workspace or a Java toolchain; the self-hosted DSL story is heavier and less siloable than a
  pure-JS npm dependency.
- **PlantUML** — mature C4 support, but requires a Java runtime — a native build toolchain, which
  the project's dependency-footprint discipline
  ([`CONTRIBUTING.md`](../../CONTRIBUTING.md), review checklist item 7, *Dependencies*) admits
  only when nothing else will do — and validates syntax, not model integrity.

LikeC4 was the only option that is a *validated model*, pure-JS (siloable, no native toolchain), and
renderable browser-free.

**Rev 4's alternatives**, for how the model reaches a reader (#115 architecture model reader):

- **Status quo: keep `likec4 codegen mermaid`.** Rejected outright: it drops every element's
  description and icon, which is most of what a C4 level is for, and it is the only rendering a
  reader of the committed diagram ever meets. The description-loss complaint that forced this
  revision is exactly what this alternative fails to fix.
- **`likec4 codegen plantuml`.** Carries full descriptions, the property this revision needs, but
  PlantUML output renders inline on neither GitHub nor this project's docs site (both need a
  PlantUML server or a local Java toolchain to turn `.puml` text into a picture) — an extra rendering
  hop the DOT/Graphviz path does not have, for no descriptive advantage over it.
- **Commit `likec4 export png` (or `jpg`).** LikeC4's own native image export needs a headless
  browser (Playwright) to rasterize, which is the specific thing this record already excludes from
  the gate ([§ Consequences](#consequences)). Putting it in `check-arch` would mean the staleness
  gate itself needs a browser — reversing this record's own posture, not extending it.
- **A *gated*, staleness-checked interactive site.** Same violation as the export-png route: `likec4
  build`'s output is a browser-rendered JavaScript application, and diffing it byte-for-byte would
  need a headless browser in the gate to prove it is current. Publishing it ungated, as this revision
  does, gets the richer view to a reader without putting a browser in `check-arch`.
- **Inline base64-encoded SVG directly in `ARCHITECTURE.md`**, avoiding a new tracked `svg`/`dot`
  extension (and the [ADR 0017 rev 9](0017-authored-language-set.md) this change also needs)
  entirely.
  Rejected once that cost was known to be one ADR rev rather than a standing burden: an inline
  base64 blob makes every diagram diff opaque (a one-pixel model change is an unreadable base64 diff)
  and matches no existing pattern in this repository, where every other generated asset is a real
  file under `docs/architecture/generated/`.

## Consequences

- **First `package.json` in the repo.** This activates the dormant npm supply-chain gates
  ([`CI.md`](../CI.md)'s dependency-vulnerability scanning). This ADR wires npm dependency tracking
  for `/docs/architecture` (pointed at that directory, so the manifest and its tracking entry sit in
  the directory of the feature they serve, per `CI.md`'s repository-shape gate); the **`npm audit` CI
  gate is deliberately left unbuilt** as a now-unblocked backlog item, to keep this change tight.
- **Rendering is fully automated in CI, and needs no headless browser — but that is now two claims,
  not one, over two different SVG paths.** LikeC4's own native image export (`likec4 export
  png`/`jpg`, and the SVG that route produces) still needs Playwright to rasterize and remains
  intentionally excluded from the gate, exactly as before. The SVG this revision admits **to** the
  gate is a different path: Graphviz rendering LikeC4's `gen dot` **text** output, which needs no
  browser at all — only the system `dot` binary — so it clears the bar the excluded path fails. Two
  formats sharing an extension is not two rules: the gate reaches one pipeline (DOT text through
  Graphviz) and stays out of the other (rasterizing a rendered view through Chromium) whatever either
  emits.
- **A new external Action dependency: `ts-graphviz/setup-graphviz`, pinned by commit SHA.** Graphviz
  itself is a system package, not an npm/Go dependency this repository already tracks, and CI needs a
  cross-platform, version-pinnable way to install it; this Action wraps `apt-get install
  graphviz=<version>` on the `ubuntu-latest` runner, pinned to an exact package version in
  `checks.yml` and `pages.yml` alike. That apt-available version is what CI (and so the committed
  SVGs) is built against — it need not, and empirically does not, match a contributor's own
  Graphviz, wherever their OS or package manager sources it from; a local `check-arch` disagreement is
  not evidence of a bug, and CI's version is the one to trust
  ([`docs/architecture/README.md`](../architecture/README.md) § Rendering).
- **A second output, the interactive site, exists and is public, but is unverified by any gate.**
  `likec4 build`'s correctness — that it reflects the current model at all — rests on nothing but the
  fact that it is produced by the same `arch-export` recipe run that regenerates the gated diagram,
  reading the model once; there is no staleness check on it, by design, and none is added. A broken
  or stale interactive site is a silent failure mode this revision accepts in exchange for not
  putting a browser in `check-arch`.
- **Model-vs-real-code drift is not auto-verified.** The staleness gate proves the *generated
  artifacts* match the *model*; it cannot prove the model matches the eventual code. That link is
  carried by the source `link`s added as code lands, and by review — not by a machine check.
- **Traceability hook is reserved, not bound.** Element tags are the mechanism for carrying Doorstop
  ids (architecture → requirements). The SRS items this was decided against were placeholder, pending
  the requirements pass in issue #18, so this decision bound none of them. Which tier an element's tag
  names, and the binding itself, are
  [ADR 0019 rev 8](0019-boundary-at-what-deploys-and-tag-tier.md)'s.
- **[ADR 0004 rev 3](0004-docs-site-sphinx-needs.md)'s deferred question is answered here, and only
  here.** That record states plainly that "how LikeC4 output enters the site (rendered Mermaid, SVG
  export, or LikeC4's interactive build) is decided at implementation and forecloses nothing here" —
  this revision is that implementation decision. ADR 0004 rev 3 itself is untouched: which toolchain
  builds the docs site was never this question's to answer, and still isn't.
- **[ADR 0017 rev 9](0017-authored-language-set.md) is revised alongside this record, in the same
  pull request, because the two cite each other.** `dot` and `svg` join, and `mmd` leaves,
  `scripts/check-languages.py`'s declared extension set — an authored-language-set change this
  record's own choice of rendering target forces, not a change this record makes itself.
- **No separate implementation ticket was filed for issue #115.** This ADR rev, its regenerated
  artifacts, and the CI and Pages workflow changes it needs all land in the one pull request that
  closes #115 — the ADR is not merged ahead of code that implements it.
- **This is a rev of an existing ADR, not a new numbered one — a departure from issue #115's own
  template checklist**, which assumes a new numbered ADR ("ADR merged: numbered per
  `docs/decisions/TEMPLATE.md`"). The owner's standing convention is that a decision within an
  existing ADR's scope is revised, not re-numbered — minting a fresh ADR number for "how does LikeC4
  output reach a reader" would fork one decision (architecture-as-code, and everything downstream of
  choosing LikeC4) across two documents for no reader's benefit, when this revision changes exactly
  the rendering-target part of what this record already owns.
