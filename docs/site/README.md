# Documentation site (Sphinx + MyST + sphinx-needs)

Renders this repository's documentation: the prose files under `docs/` unchanged (no frontmatter, no
in-source directives — see [ADR 0004](../decisions/0004-docs-site-sphinx-needs.md)), the repo-root
files (`README.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CLAUDE.md`) via thin include shims, and a
generated, click-through view of the Doorstop requirements tree
([`../requirements/`](../requirements/README.md), [ADR
0002](../decisions/0002-requirements-management-doorstop.md)).

**Dev-only and siloed here** (FOUNDATIONS §2): its pinned requirements file and venv live in this
directory; nothing depends on it at app build or runtime. Doorstop is the canonical requirements
source and gate — this silo only renders it.

## Layout

```
docs/site/
  requirements-dev.txt   exact-pinned Sphinx + MyST + sphinx-needs + theme
  conf.py                Sphinx configuration (srcdir is docs/, confdir is here)
  index.md               root toctree shim: an {include} of ../../README.md plus the site's toctrees
  contributing.md        {include} shim for ../../CONTRIBUTING.md
  security.md             {include} shim for ../../SECURITY.md
  CLAUDE.md               {include} shim for ../../CLAUDE.md (case matches the link CONTRIBUTING.md uses)
  traceability.md         hand-authored needtable / matrix views
  doorstop_to_needs.py    thin, presentation-free transform: Doorstop YAML -> sphinx-needs MyST
  _static/needs-furo.css  maps sphinx-needs' colors onto furo's light/dark theme variables
  generated/              build-time output — regenerated on every build, gitignored
    requirements/items/   one page per requirement item — the definition every id link resolves to
    requirements/{sys,srs,tst}.md  one sheet per document, pulling its items together via needextract
  _build/                 built HTML, gitignored
  .venv/                  local venv, gitignored
```

`index.md`, `contributing.md`, `security.md`, and `CLAUDE.md` are the only structural concession
Sphinx demands (ADR 0004): each is a pure `{include}` of its repo-root counterpart, using MyST's
`relative-docs` option to rewrite that file's root-relative links (e.g. `docs/FOUNDATIONS.md`) to
resolve from inside the silo. The included file's own top heading becomes the page title — no
hand-written prose duplicates it.

## Building

Requires a local venv — siloed here beside the tooling it serves — with the pinned packages
([`requirements-dev.txt`](requirements-dev.txt)):

```sh
python3 -m venv docs/site/.venv
docs/site/.venv/bin/pip install -r docs/site/requirements-dev.txt
```

Then, from the repo root:

```sh
just site-install    # the two commands above
just site-build      # regenerate generated/, then build the site with -W
just check-site      # the CI gate: just site-build, part of `just verify`
```

`just check-site` runs the exact commands CI runs (see
[`../../.github/workflows/checks.yml`](../../.github/workflows/checks.yml), job `docs-site`): the
transform, then `sphinx-build -W -b html -c docs/site docs docs/site/_build/html`. `-W` turns any
Sphinx warning — a broken cross-reference, an orphaned page — into a build failure.

## The Doorstop -> sphinx-needs transform

[`doorstop_to_needs.py`](doorstop_to_needs.py) reads the YAML items under
[`../requirements/{sys,srs,tst}/`](../requirements/README.md) with plain PyYAML — it does not import
Doorstop, so none of that tool's dependency weight enters this silo. For each item it writes one page
under `generated/requirements/items/` holding a single `{sys}`/`{srs}`/`{tst}` sphinx-needs directive: id and
title and text carried across verbatim, parent links from Doorstop's `links`, status from `active`.
That item page is the definition every `id` link in the site resolves to, so a link's target always
shows the requirement with both its parent and child links. Each document also gets one sheet page
(`sys.md`/`srs.md`/`tst.md`) that pulls its type's items together with a `needextract` filter and
reaches them via a glob toctree — structure, not presentation, so the ADR 0004 thin-transform
boundary holds.

The transform is deliberately presentation-free otherwise — no styling, no reordering beyond a
stable sort by id. The traceability *views* — `needtable`s, the full matrix — are hand-authored in
[`traceability.md`](traceability.md), which is legitimate silo content distinct from the transform.

The ADR pages nest under [`../decisions/README.md`](../decisions/README.md) in the nav via a
`source-read` hook in [`conf.py`](conf.py) that appends a hidden glob toctree to that one document
in memory at build time — the canonical file stays byte-identical, and a new ADR appears in the nav
with no edit anywhere.

`generated/` is regenerated by every `site-build`/`check-site` run; it is gitignored and never
hand-edited.

## Deployment

A separate workflow, [`../../.github/workflows/pages.yml`](../../.github/workflows/pages.yml), builds
this site and deploys it to GitHub Pages on push to `main`. It runs the same build commands as
`check-site` and holds `pages: write` + `id-token: write` via OIDC — no stored credentials.
`checks.yml` stays read-only (ADR 0004).

No document in this repository references the deployed site's URL: the repo stays self-contained
(`SYS001`) and loses nothing if Pages disappears.

## What this silo deliberately does not do

- **No versioned docs, no PDF export, no custom theming beyond a stock theme** — each is abstraction
  without a consumer (FOUNDATIONS §5).
- **No `needflow` link graph.** sphinx-needs' `needflow` directive needs either PlantUML (a JVM
  dependency) or Graphviz, and Graphviz is not guaranteed to be present on every machine this silo is
  built on; see the note in [`traceability.md`](traceability.md).
